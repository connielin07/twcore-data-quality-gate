# Day11 - 完成 Quantity 可讀單位存在性規則
> 摘要
> Day 10 已完成第四條交換契約規則 `LAB-CODE-001`，確認 `Observation.code` 是否包含合作方允許的 LOINC coding。Day 11 接著實作第五條規則 `LAB-UNIT-001`：當 `Observation.value[x]` 是 `Quantity` 時，`valueQuantity.unit` 必須存在，讓檢驗數值不只機器可解析，也能被合作方系統與人工流程直接閱讀。

### 為什麼 unit 規則要放在 UCUM 規則之前？

Day 10 的 LOINC 規則回答的是：

```text
這筆 Observation 是不是合作方允許接收的檢驗項目？
```

例如：

```text
Observation.code.coding = http://loinc.org|2345-7
```

但就算檢驗項目是允許的，檢驗結果本身仍然可能缺少必要的單位資訊。

例如一筆血糖結果可能長這樣：

```json
"valueQuantity": {
  "value": 95,
  "system": "http://unitsofmeasure.org",
  "code": "mg/dL"
}
```

這筆資料有 `value`，也有 UCUM 相關的 `system` 與 `code`。

但缺少人類可讀的：

```text
valueQuantity.unit
```

如果合作方的畫面或報表直接顯示檢驗結果，缺少 `unit` 會讓結果變成：

```text
95
```

而不是：

```text
95 mg/dL
```

FHIR parser 可能可以解析這筆資料。

TW Core Profile 也不一定會把這個合作方顯示需求視為交換阻擋條件。

但從交換情境來看，合作方會問的是：

> 這筆 Quantity 檢驗結果是否具有可直接閱讀的單位？

這就是 `LAB-UNIT-001` 要處理的問題。

它不是完整 UCUM validation。

它是 Quantity 可讀單位存在性檢查。

### 今天的實作範圍

今天新增或修改的範圍只有：

- `LabUnit001ObservationQuantityUnitRule`
- `LabUnit001ObservationQuantityUnitRuleTests`
- 2 份 `LAB-UNIT-001` 專用 fixture
- Day 11 journal

先把第五條規則的行為固定下來，會比提早擴張 UI 或契約版本功能更重要。

今天完成後，六條核心交換規則的進度變成：

```text
Observation.subject → Patient
DiagnosticReport.result → Observation
DiagnosticReport.subject 與 Observation.subject → 同一 Patient
Observation.code → 契約允許 LOINC
Observation.valueQuantity.unit → 可讀單位存在
```

剩下最後一條：

```text
Observation.valueQuantity.system/code → 契約允許 UCUM 單位集合
```

### 為什麼今天不直接做 UCUM？

`Quantity` 裡常見的單位欄位有三個：

```text
valueQuantity.unit
valueQuantity.system
valueQuantity.code
```

它們處理的是不同層次。

`unit` 比較接近顯示與人工閱讀需求：

```json
"unit": "mg/dL"
```

`system` 與 `code` 比較接近機器判讀與標準化交換需求：

```json
"system": "http://unitsofmeasure.org",
"code": "mg/dL"
```

Day 11 先做 `LAB-UNIT-001`，只確認：

```text
當 value[x] 是 Quantity 時，unit 必須存在
```

Day 12 再做 `LAB-UNIT-002`，確認：

```text
system = http://unitsofmeasure.org
code   in 合作契約允許的 UCUM 單位集合
```

這樣拆開的好處是，錯誤訊息會比較清楚。

缺少可讀單位時，使用者看到的是：

```text
請補上合作方可讀的檢驗單位，例如 mg/dL。
```

UCUM system 或 code 不符合契約時，Day 12 再回另一個更精準的錯誤。

### LAB-UNIT-001 要處理什麼？

`LAB-UNIT-001` 只看：

```text
Observation.value[x]
Observation.valueQuantity.unit
```

規則判斷條件如下：

```text
value[x] is Quantity
unit exists and is not blank
```

只要 `Observation.value[x]` 是 `Quantity`，而且 `valueQuantity.unit` 有值，就回 `PASS`。

如果 `Observation.value[x]` 是 `Quantity`，但 `unit` 缺少或空白，就回 `FAIL`。

如果 Bundle 沒有 Observation，或 Observation 的 value 不是 Quantity，就回 `NOT_APPLICABLE`。

目標是展示「交換契約可以補上 Profile 驗證之外的合作方顯示需求」。

### Day 11 的結果分類

`LAB-UNIT-001` 的分類順序如下：

```text
Bundle 沒有 Observation → NOT_APPLICABLE
Observation 沒有 value[x] → NOT_APPLICABLE
Observation.value[x] 不是 Quantity → NOT_APPLICABLE
Observation.valueQuantity.unit 缺少或空白 → FAIL
Observation.valueQuantity.unit 有值 → PASS
```

這裡有三個容易混淆的地方。

第一，沒有 `Observation` 時不是 `FAIL`。

因為這條規則的適用對象不存在，所以回：

```text
NOT_APPLICABLE
```

第二，`Observation.value[x]` 不是 Quantity 時也不是 `FAIL`。

例如：

```json
"valueString": "positive"
```

這筆資料不一定錯。

它只是超出 `LAB-UNIT-001` 的檢查範圍。

所以回：

```text
NOT_APPLICABLE
```

第三，Day 11 沒有檢查 `system` 與 `code`。

例如：

```json
"valueQuantity": {
  "value": 95,
  "unit": "mg/dL"
}
```

在 `LAB-UNIT-001` 會先通過。

至於是否具有：

```text
system = http://unitsofmeasure.org
code   = mg/dL
```

那是 `LAB-UNIT-002` 的責任。

```text
PASS
FAIL
NOT_APPLICABLE
```

後續加入 `LAB-UNIT-002` 時，才有穩定的 Quantity unit 行為可以比對。

### 實作

Day 11 新增：

```text
src/main/java/com/twlab/qualitygate/validation
└─ LabUnit001ObservationQuantityUnitRule.java
```

規則仍然實作同一個介面：

```java
public class LabUnit001ObservationQuantityUnitRule implements ContractRule {

  public static final String RULE_CODE = "LAB-UNIT-001";

  @Override
  public String ruleCode() {
    return RULE_CODE;
  }

  @Override
  public List<RuleResult> validate(Bundle bundle) {
    // ...
  }
}
```

代表 Day 7 建立的 `ContractRule` 介面仍然可以繼續使用。

第五條規則也不需要新的資料模型。

核心邏輯分成三步：

```text
找出 Bundle 內所有 Observation
        ↓
確認 Observation.value[x] 是否為 Quantity
        ↓
確認 valueQuantity.unit 是否存在且不是空白
```

判斷邏輯如下：

```java
private boolean hasReadableUnit(Quantity quantity) {
  return quantity.hasUnit() && !quantity.getUnit().isBlank();
}
```

實際顯示值則收斂成：

```java
private String actualUnit(Quantity quantity) {
  return hasReadableUnit(quantity) ? quantity.getUnit() : "N/A";
}
```

這樣缺少 unit 時，`RuleResult.actual` 會是：

```text
N/A
```

而不是空字串或 `null`。

### 常見錯誤 & 排查

1. 把 `LAB-UNIT-001` 誤當成完整 UCUM validation

`LAB-UNIT-001` 不是完整 UCUM validation。

它沒有檢查：

```text
system = http://unitsofmeasure.org
code 是否在允許集合
```

它只檢查：

```text
valueQuantity.unit 是否存在
```

所以文章裡應該稱為「可讀單位存在性檢查」，不要稱為完整 UCUM 驗證。

2. 把非 Quantity value 判成失敗

`Observation.value[x]` 有很多型別。

如果資料是：

```json
"valueString": "positive"
```

它不是 `LAB-UNIT-001` 的適用對象。

這時應該回：

```text
NOT_APPLICABLE
```

而不是 `FAIL`。

3. 只檢查 `system/code`，忘記 `unit`

Day 12 會處理 `system/code`。

但 Day 11 的重點是可讀單位：

```text
valueQuantity.unit
```

如果只看 `system/code`，就無法展示「機器標準化」與「人工可讀」是兩個不同層次。

4. 缺少 unit 時回傳空字串或 null

規則結果裡的 `actual` 應該穩定顯示：

```text
N/A
```

這樣測試、畫面與文章說明都比較一致。

### 這和「能不能交換」有什麼關係？

前四條規則目前回答的是：

```text
資料鏈是否接得起來？
檢驗項目是否屬於合作方允許集合？
```

Day 11 的 `LAB-UNIT-001` 回答的是：

```text
檢驗數值是否具有合作方可直接閱讀的單位？
```

也就是說，就算資料長這樣：

```text
DiagnosticReport.result → Observation/obs-1
Observation.subject     → Patient/patient-1
Observation.code        → http://loinc.org|2345-7
```

還是可能因為：

```text
Observation.valueQuantity.unit = N/A
```

而被交換契約擋下。

這不是 JSON 格式錯誤。

也不一定是 TW Core Profile 錯誤。

它比較適合被歸類為：

```text
Exchange Contract: FAILED
```

這也是資料品質閘門要補上的地方：

```text
標準驗證告訴我們 Resource 結構是否合理。
交換契約規則告訴我們這份資料是否符合合作方接收與閱讀條件。
```
